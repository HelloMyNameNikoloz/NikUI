# NikUI, as an app

A native shell around **the same client the editor runs**. Not a second client —
the moment there are two they drift, and everything in this repository is
arranged to stop that.

```
npm run app            # build the bundle and sync both platforms
npm run app:android    # build, sync, and run on a connected phone
npm run test:app       # drive the real bundle in a real browser
cd app && npm test     # check the bundle is still a copy, not a fork
```

## What is where

    app/capacitor.config.json   appId, the dark field colour, the schemes
    app/shell/                  the app's own screens: app.css, app.js,
                                connect.js, settings.js
    app/tools/build.js          builds www/ from media/ — never edited by hand
    app/tools/icons.js          launcher icons from the same mark as everything else
    app/tools/build.test.js     proves www/ is a copy of media/, file by file
    app/tools/app.check.js      the app, driven in a browser against a real laptop
    app/www/                    generated, git-ignored
    app/android, app/ios        the native projects, committed

## The one rule

**Nothing in `www/` is written by hand.** Every client file is copied from
`media/`, and the conversation screen is generated by the very same
`renderPage()` the editor's panel uses. `cd app && npm test` fails the day
somebody edits a copy instead of the original, or adds a file to the panel and
forgets the app.

What is app-only is the part a browser never needed: connecting to a laptop in
the first place, and settings.

## What the app changes about the client

Three small things, all of them generalisations rather than special cases — the
client now works whether it was *served* by a laptop or *bundled* by an app:

- `transport.js` accepts an absolute socket address and keeps its scheme. A
  served page still works out where it came from.
- `home.js` and `transport.js` ask where a conversation lives instead of
  assuming `/s/<id>`.
- `remote.js` tells an app origin apart from a web page. A WebView serves its
  bundle from a fixed origin of its own, so everything the app asks is
  cross-origin — the exact shape the Origin check exists to refuse. Three
  origins are allowed (`https://localhost`, `capacitor://localhost`,
  `ionic://localhost`), never `*`, never with credentials, and loopback origins
  only while the request itself is loopback and nothing is forwarding.

## The screens

**Connect** — three fields and one button. The address and the laptop's key
fingerprint fill themselves in from a pairing link when there is one; the device
names itself; the key is made before the button is pressed so tapping it does
one thing and does it now.

**Instances** — the fleet, live, with the connection state in the bar.

**Conversation** — the client, unchanged: the same transcript, composer, queue
and dashboard the panel draws.

**Settings** — is it connected, and how fast. What this device is allowed, and
where that is granted. Which laptop, which key is pinned, when it was paired.
Text size. Versions of both the app and the client it carries. Copy diagnostics.
And one way to undo it, which asks twice.

## Design

Dark only, and pinned dark: `browser.css` switches its palette on the phone's
setting, which is right for a page in a browser and wrong for an app whose own
chrome is dark. The vocabulary is the product's — the near-black field, the four
status colours, SF Pro, the 8pt rhythm — arranged the way iOS arranges things:
grouped inset lists, hairline separators, 44pt targets, one clear action per
screen. The chevron and the gear are drawn in CSS, so the app carries no icon
font and no sprite sheet.

## What is not here yet

Phases 2 to 6 of the app plan: the key in the Secure Enclave and Android
Keystore with a biometric gate, TLS pinning, an app-only mode that stops the
laptop serving HTML at all, native push, and the store logistics. The protocol
does not change for any of them — the laptop already verifies a P-256 signature
and does not care where the key lives.
